### V1: The Auditable Security Platform Blueprint

This blueprint outlines a deliberately constrained first version. The goal of V1 is to execute a simple, safe recon task (e.g., discovering open ports or subdomains) while proving the architecture: generating an immutable audit trail and respecting the policy engine.

#### 1. The Database Schema (PostgreSQL)

The database is the source of truth for the entire platform. It must strictly model the engagement boundaries and the immutable audit log.

**Core Entities:**

* **`Engagement`**: The overriding authorization container.
  * `id` (UUID, Primary Key)
  * `client_id` (FK to Client)
  * `start_time` (Timestamp)
  * `end_time` (Timestamp)
  * `authorization_doc_hash` (String - cryptographic hash of the signed rules of engagement)

* **`Scope`**: Defines what the agent is allowed to touch.
  * `id` (UUID, Primary Key)
  * `engagement_id` (FK to Engagement)
  * `target_type` (Enum: IP, Domain, CIDR)
  * `target_value` (String)
  * `is_excluded` (Boolean - explicit exclusions override inclusions)

* **`PolicyRule`**: The rules enforced by the Policy Engine.
  * `id` (UUID, Primary Key)
  * `engagement_id` (FK to Engagement)
  * `tool_category` (Enum: Recon, Active Probe, Exploit)
  * `action` (Enum: Allow, Deny, RequireHuman)

* **`DecisionLog` (The Immutable Audit Trail):** Every step the agent takes.
  * `id` (UUID, Primary Key)
  * `engagement_id` (FK to Engagement)
  * `timestamp` (Timestamp)
  * `phase` (String - e.g., "Recon")
  * `observation` (Text - What did the agent see?)
  * `hypothesis` (Text - What does the agent think?)
  * `proposed_action` (Text - What tool/command does it want to run?)
  * `policy_decision` (Enum: Approved, Denied, PendingHuman)
  * `result_status` (Enum: Success, Failed, Blocked)
  * `evidence_id` (FK to Evidence - nullable until completed)

* **`Evidence`**: The raw output of tools.
  * `id` (UUID, Primary Key)
  * `decision_log_id` (FK to DecisionLog)
  * `data_type` (Enum: JSON, RawText, Screenshot, PCAP)
  * `storage_path` (String - URI to Object Storage)
  * `hash` (String - cryptographic hash of the evidence file to prove it wasn't tampered with)

#### 2. The Agent State Machine

V1 should use a highly constrained state machine, preventing the LLM from getting stuck in loops or hallucinating actions. The agent must traverse these states linearly for every action.

**The Loop:**

1. **`OBSERVE_STATE`**: The agent analyzes existing `Evidence` or `Scope` data.
2. **`HYPOTHESIZE_STATE`**: The agent formulates a hypothesis based on observations.
3. **`PROPOSE_ACTION_STATE`**: The agent selects a specific tool and parameters to test the hypothesis.
4. **`POLICY_EVALUATION_STATE`** (System Controlled, not AI): The Policy Engine intercepts the proposed action.
   * If **Approved** -> Go to `EXECUTE_STATE`.
   * If **Denied** -> Return to `OBSERVE_STATE` with denial reason.
   * If **RequireHuman** -> Pause state machine until human input.
5. **`EXECUTE_STATE`** (System Controlled, not AI): The Tool Manager executes the requested tool in an isolated container.
6. **`ANALYZE_EVIDENCE_STATE`**: The agent receives the raw output, generates findings, and updates the attack graph.
7. **Loop restarts.**

#### 3. The Tool Interface

The AI never receives a raw terminal or shell access. It interacts with the Tool Manager via a strictly typed JSON schema.

**Example Tool Definition (Provided to the LLM):**

```json
{
  "name": "dns_enumeration",
  "description": "Perform DNS enumeration (A, AAAA, MX, TXT records) on a target domain.",
  "parameters": {
    "target_domain": {
      "type": "string",
      "description": "The fully qualified domain name to enumerate."
    }
  },
  "required_authorization_level": "LOW"
}
```

**Example Tool Request (Generated by the LLM in `PROPOSE_ACTION_STATE`):**

```json
{
  "action": "dns_enumeration",
  "parameters": {
    "target_domain": "example.com"
  },
  "justification": "Initial scope includes example.com; DNS enumeration is required to identify subdomains and mail infrastructure."
}
```

#### 4. The Policy Enforcement Engine

This is the gatekeeper. It is a deterministic, non-AI component that evaluates the LLM's `Tool Request` against the `Engagement` database.

**Policy Check Logic (Pseudocode):**

```typescript
function evaluateProposedAction(actionRequest, engagementId) {
  const engagement = fetchEngagement(engagementId);

  // Check 1: Time Window
  if (currentTime() < engagement.start_time || currentTime() > engagement.end_time) {
     return { status: "DENIED", reason: "Outside authorized time window." };
  }

  // Check 2: Target Scope
  const target = actionRequest.parameters.target_domain || actionRequest.parameters.target_ip;
  if (isExcludedTarget(target, engagement.excluded_targets)) {
     return { status: "DENIED", reason: `Target ${target} is explicitly excluded.` };
  }
  if (!isInScope(target, engagement.targets)) {
     return { status: "DENIED", reason: `Target ${target} is not in authorized scope.` };
  }

  // Check 3: Allowed Techniques/Tools
  const policyRule = fetchPolicyRule(actionRequest.action, engagementId);
  if (policyRule.action === "Deny") {
     return { status: "DENIED", reason: `Tool ${actionRequest.action} is prohibited for this engagement.` };
  }
  if (policyRule.action === "RequireHuman") {
     return { status: "PENDING_HUMAN", reason: "Human review required." };
  }

  // If all checks pass:
  return { status: "APPROVED" };
}
```

### Why This Approach Wins

By building the architecture this way, the LLM is relegated to the role of an "intelligent analyst" rather than a "hacker with a terminal."

1. **Isolation:** The AI decides *what* to do; the system determines *if* it is allowed and *how* to execute it safely.
2. **Auditability:** Every tool execution is linked directly back to the `DecisionLog`, which contains the LLM's justification and the exact time the Policy Engine approved it.
3. **Reproducibility:** A human analyst can read the `DecisionLog` and see exactly why the agent chose a specific path, making the final report defensible.
